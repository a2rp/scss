# Sass CLI, watch mode, and build options - Q&A

This Q&A focuses on Dart Sass’s command-line interface. Exact option support can depend on the installed Sass version; use the CLI’s <code>--help</code> output and the official documentation linked at the end.

## 1. What does the Sass CLI do?

The CLI reads Sass or CSS source and writes compiled CSS, either to a file, a mapped output path, or standard output. It also provides modes for compiling multiple files, watching source changes, and configuring output.

## 2. What is one-to-one mode?

It compiles one input file to one output file:

~~~sh
sass input.scss output.css
~~~

If no output file is given, Sass prints the CSS to standard output.

## 3. What is many-to-many mode?

It compiles one or more inputs to corresponding outputs. A file pair is written with a colon:

~~~sh
sass src/light.scss:public/light.css src/dark.scss:public/dark.css
~~~

It can also map a directory of Sass files to a directory of CSS files.

## 4. How are Sass input files parsed?

Files ending in <code>.scss</code> are parsed as SCSS, files ending in <code>.sass</code> as indented Sass syntax, and CSS files as CSS. Use <code>--indented</code> or <code>--no-indented</code> when the default based on filename is not appropriate.

## 5. Does directory compilation emit partials?

No. When Sass compiles a directory, files whose names begin with an underscore are ignored as standalone outputs. They can still be loaded as dependencies by entry files.

## 6. Should I compile a directory or explicit files?

Use explicit file mappings when the set of entry points is small and known. Use directory mapping when each non-partial Sass file in the source directory is intended to compile to its own CSS output.

Do not use directory mode if it would turn helper or experimental files into unwanted standalone stylesheets.

## 7. How does --watch work?

Sass performs an initial compilation and remains open, recompiling outputs when watched files change. It behaves like an initial update followed by continued watching.

Use it for an active development session, not a one-time release build.

## 8. Does Sass watch every @use dependency automatically?

No. Sass watches directories passed directly, parent directories of filenames passed, and load paths. It does not automatically add every additional folder referenced by <code>@use</code> or <code>@forward</code>.

If a dependency is outside watched locations, add the source directory or a suitable load path to the command.

## 9. Why might watch mode miss a file change?

The edited file may be outside the watched directories, or the filesystem may not deliver change notifications reliably. Check the watch paths first. If notification delivery is the issue, try <code>--poll</code>.

## 10. What does --poll do?

<code>--poll</code> makes Sass periodically check files for changes instead of relying on the operating system’s file notifications. It can help on some remote filesystems and must be used together with <code>--watch</code>.

~~~sh
sass --watch --poll src/styles:public/css
~~~

Polling is unnecessary overhead when normal notifications work reliably.

## 11. What is the difference between --watch and --update?

<code>--update</code> performs a compilation pass for changed outputs and exits. <code>--watch</code> does an initial update and then stays open to continue compiling future changes.

Use update mode in a one-time incremental build; use watch mode during interactive development.

## 12. How does --update decide what to compile?

Sass compares source and dependency modification times with the existing CSS output. It recompiles outputs whose dependencies are newer. If a CSS output is missing, Sass creates it.

This is an incremental CLI behavior, not a replacement for a package manager or full application build graph.

## 13. What does --stop-on-error do?

When compiling multiple inputs, Sass can continue to process other files after one input fails. <code>--stop-on-error</code> tells it to stop on the first error:

~~~sh
sass --stop-on-error src/themes:public/css/themes
~~~

This can shorten CI output when one failure is sufficient to fail the build.

## 14. Which CSS output styles are supported?

Dart Sass supports <code>expanded</code> and <code>compressed</code>. Expanded is the default and is readable. Compressed removes formatting characters to produce compact output.

~~~sh
sass --style=expanded input.scss output.css
sass --style=compressed input.scss output.css
~~~

## 15. Does compressed CSS change how styles work?

No. It changes formatting, not the intended CSS behavior. It does not fix inefficient selectors or reduce the number of rules; review the generated CSS separately if those are concerns.

## 16. Are source maps generated by default?

Yes. Dart Sass generates source maps by default for emitted CSS files. The map helps browser tools trace compiled declarations back to Sass source.

Use <code>--no-source-map</code> to disable map generation for a particular output.

## 17. What are relative and absolute source-map URLs?

Relative URLs point from the map’s location to source files and are the default. Absolute URLs use file URLs tied to the machine that compiled the CSS, so they generally do not work after moving the build to another machine.

Use relative URLs for normal project builds unless a workflow has a specific reason for another choice.

## 18. What does --embed-sources do?

It embeds the contents of Sass source files in the source map. This can make the map larger, but source text is available along with the map when files are not otherwise served.

Use it only when that portability is needed.

## 19. What does --embed-source-map do?

It embeds source-map data into the generated CSS instead of writing a separate map file. This changes how debugging data is delivered and can increase CSS size.

Do not enable it unless the asset workflow needs an embedded map.

## 20. What is a Sass load path?

A load path adds a directory Sass searches when resolving module URLs:

~~~sh
sass --load-path=src/shared input.scss output.css
~~~

You can provide multiple paths. Earlier paths take precedence over later ones. A load path changes where Sass looks; it does not rewrite relative URLs in the source.

## 21. What is --pkg-importer=node?

It enables Dart Sass’s Node package importer for supported <code>pkg:</code> module URLs. The CLI documentation lists it as supported beginning in Dart Sass 1.71.0.

Check the version installed in the project and the package’s Sass entry points before using it. It is not required for ordinary relative module loading.

## 22. What is --error-css?

When compiling to a file, Dart Sass enables error CSS by default. If compilation fails, it can write CSS containing a visible diagnostic for browser inspection; the compiler still reports the error.

This is a debugging aid, not valid release CSS.

## 23. What does --no-error-css change?

It disables the diagnostic CSS output. In watch or update mode, Sass deletes CSS files instead when an error occurs.

Choose based on how the development server and application should behave after a failed compile.

## 24. What does --charset do?

When non-ASCII characters occur, Sass may emit a charset marker by default: a <code>@charset</code> declaration in expanded output or a UTF-8 byte-order mark in compressed output. <code>--no-charset</code> disables that behavior.

Use it only when the output encoding and serving pipeline are known.

## 25. What is the difference between --verbose, --quiet, and --quiet-deps?

- <code>--verbose</code> emits all deprecation warnings instead of limiting repeated warnings.
- <code>--quiet</code> silences warnings and debug output broadly.
- <code>--quiet-deps</code> suppresses dependency deprecation warnings while keeping first-party warnings visible.

Use quiet options selectively. They should not hide warnings in the project’s own Sass.

## 26. Can I turn a deprecation into an error?

Yes. <code>--fatal-deprecation</code> accepts supported deprecation IDs or a Sass version threshold:

~~~sh
sass --fatal-deprecation=import input.scss output.css
~~~

This can make a migration requirement enforceable in CI. Confirm the ID exists in the installed Sass version and review dependencies before enabling the flag.

## 27. What does --trace show?

<code>--trace</code> prints a fuller compiler stack trace after an error. Use it when the normal source location and error message do not explain the failure. It is usually unnecessary for everyday compilation.

## 28. What is --stdin for?

It tells Sass to read source from standard input:

~~~sh
"h1 { color: red; }" | sass --stdin output.css
~~~

Standard input cannot be combined with many-to-many mode. For maintained project styles, named Sass files are generally easier to trace.

## 29. Can I use --indented to parse stdin?

Yes. Standard input has no filename extension to identify its syntax. Use <code>--indented</code> to tell Sass that stdin contains indented Sass syntax. In many-to-many mode the option applies to all input files, so use it deliberately.

## 30. What does --interactive do?

It starts a prompt where SassScript expressions can be entered and evaluated. It can be useful for exploring a calculation, unit conversion, or Sass value without creating a project file.

It is not a stylesheet build mode.

## 31. How do I check which options my installed CLI supports?

Run:

~~~sh
sass --help
sass --version
~~~

For a project-local npm dependency, use <code>npx sass --help</code> and <code>npx sass --version</code>. This is especially useful for options introduced in later Dart Sass versions.

## 32. Does a failed compilation return an error status?

Yes. Sass reports a compilation failure through its command status. An npm script or CI runner should preserve that status so a later command cannot make the overall build appear successful.

## 33. Which options are useful for local development?

Common choices are <code>--watch</code>, expanded output, and source maps. Polling is only needed when change notifications are unreliable. Keep the command focused on the entry points being edited.

## 34. Which options are useful for CI or release builds?

A release build often compiles once and may use compressed output. CI can use <code>--stop-on-error</code> for multi-entry builds and may enforce selected deprecations.

Whether to emit source maps depends on the project’s debugging and deployment needs; there is no universal setting.

## 35. What are common CLI mistakes?

- Watching a directory that does not include edited dependencies.
- Using directory mode when files should not become independent outputs.
- Leaving watch mode running in a one-time build.
- Assuming <code>--update</code> cleans arbitrary stale output files.
- Embedding maps and sources without considering asset size.
- Suppressing warnings instead of fixing first-party deprecations.
- Using a flag unsupported by the project’s installed Sass version.
- Forgetting that a compiler error should fail the enclosing build.
