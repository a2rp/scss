# 014 - Comments and Generated CSS Output

## Learning goals

After this lesson, you should be able to:

- Distinguish silent Sass comments from CSS comments in SCSS.
- Choose comments that should or should not appear in generated CSS.
- Preserve a license or attribution comment in compressed output.
- Use interpolation in a CSS comment.
- Recognize SassDoc documentation comments.
- Compile a stylesheet with expanded or compressed output.
- Understand how source maps connect generated CSS to its Sass sources.
- Inspect generated CSS without confusing it with the original SCSS.

## 1. Why comments and output matter

SCSS is source code. Browsers receive the CSS generated by Sass, not the SCSS file itself. Sass evaluates variables, mixins, functions, loops, and nesting while producing that CSS.

~~~scss
$brand: #2457c5;

.button {
  color: white;
  background-color: $brand;
}
~~~

Generated CSS:

~~~css
.button {
  color: white;
  background-color: #2457c5;
}
~~~

Comments may be intended only for people working on the SCSS, or they may need to remain in the generated stylesheet. Choose the comment syntax based on that purpose.

## 2. Silent comments with //

A double-slash comment starts with // and continues to the end of the line. Sass removes it from generated CSS.

~~~scss
// Button colors come from the design token map.
$brand: #2457c5;

.button {
  // Keep the foreground readable on the brand surface.
  color: white;
  background-color: $brand;
}
~~~

Generated CSS:

~~~css
.button {
  color: white;
  background-color: #2457c5;
}
~~~

Use silent comments for implementation notes that belong only in the Sass source.

## 3. CSS comments with /* ... */

A block comment starts with /* and ends with */. When it appears where a statement is allowed, Sass emits it as a CSS comment in expanded output.

~~~scss
/* Brand button styles */
.button {
  color: white;
  background-color: #2457c5;
}
~~~

Expanded CSS:

~~~css
/* Brand button styles */
.button {
  color: white;
  background-color: #2457c5;
}
~~~

These comments are sometimes called loud comments because they can be heard in the generated CSS.

## 4. Comments in compressed output

Dart Sass removes ordinary block comments in compressed mode. This keeps the production CSS smaller.

Source SCSS:

~~~scss
/* Internal implementation note */
.button {
  color: white;
  background-color: #2457c5;
}
~~~

With compressed output, the ordinary comment is removed.

A comment that begins with /*! is preserved in compressed output:

~~~scss
/*! Project name and license information */
.button {
  color: white;
  background-color: #2457c5;
}
~~~

Compressed CSS:

~~~css
/*! Project name and license information */.button{color:white;background-color:#2457c5}
~~~

Use the preserved form only for comments that need to ship, such as license notices or required attribution. Avoid putting private notes or secrets in a comment that will be published.

## 5. Interpolation in a CSS comment

A loud comment can contain Sass interpolation. Sass evaluates the expression before emitting the comment.

~~~scss
$release: "2.4.0";

/* Stylesheet release: #{$release} */
~~~

Generated CSS includes:

~~~css
/* Stylesheet release: 2.4.0 */
~~~

Only use this when a generated comment is useful to readers of the CSS. Silent comments are not emitted, so they are not a way to create generated documentation.

## 6. Comments can appear where whitespace is allowed

SCSS supports comments in places where CSS allows whitespace, including between selector parts. Sass removes the comment while preserving the intended token separation.

~~~scss
.card /* card variant */ .compact {
  padding: 0.5rem;
}
~~~

Generated selector:

~~~css
.card .compact {
  padding: 0.5rem;
}
~~~

Use this sparingly. A comment between selector tokens can make the source harder to scan, so a separate explanation above the rule is usually clearer.

## 7. SassDoc comments

A triple-slash comment written directly above a variable, mixin, function, or placeholder is a documentation comment used by SassDoc tooling.

~~~scss
/// Applies a consistent focus ring to an interactive control.
///
/// @param {Color} $color
///   The ring color.
/// @param {Length} $width
///   The ring width.
@mixin focus-ring($color, $width: 2px) {
  outline: $width solid $color;
  outline-offset: 2px;
}
~~~

Sass treats /// as a silent comment, so it is not emitted into CSS. A documentation tool can read its Markdown and annotations to generate API documentation.

Use SassDoc when you are documenting a reusable Sass library. For ordinary project styles, a concise // comment is often enough.

## 8. Compile SCSS to CSS

The Dart Sass CLI accepts an input SCSS file and an output CSS file:

~~~sh
sass src/styles.scss public/styles.css
~~~

This is one-to-one mode: one Sass input is written to one CSS output. If the output path is omitted, CSS is printed to the terminal.

~~~sh
sass src/styles.scss
~~~

The Sass source is compiled, so the generated CSS contains resolved values and flattened selectors.

## 9. Expanded and compressed styles

The output style controls formatting, not the meaning of the styles.

### Expanded output

Expanded is the default. It puts selectors and declarations on separate lines:

~~~sh
sass --style=expanded src/styles.scss public/styles.css
~~~

Example output:

~~~css
.button {
  color: white;
  background-color: #2457c5;
}
~~~

Expanded CSS is easier to inspect and debug.

### Compressed output

Compressed output removes as many extra characters as possible and writes the stylesheet on one line:

~~~sh
sass --style=compressed src/styles.scss public/styles.min.css
~~~

Example output:

~~~css
.button{color:white;background-color:#2457c5}
~~~

Compressed CSS is compact for delivery. It is less convenient to edit or debug by hand. Keep the Sass source as the editable source of truth.

## 10. SCSS nesting becomes ordinary CSS selectors

Sass nesting is resolved during compilation. The browser receives the resulting selectors.

~~~scss
.navigation {
  display: flex;

  a {
    color: #2457c5;

    &:hover {
      text-decoration: underline;
    }
  }
}
~~~

Generated CSS:

~~~css
.navigation {
  display: flex;
}

.navigation a {
  color: #2457c5;
}

.navigation a:hover {
  text-decoration: underline;
}
~~~

The generated output is a useful place to confirm that nested selectors expand as intended.

## 11. Variables and mixins do not appear as Sass syntax

Sass variables and mixins are build-time tools. Their evaluated declarations appear in CSS; the variable and mixin definitions do not.

~~~scss
$gap: 1rem;

@mixin card-surface {
  padding: $gap;
  border: 1px solid #d0d5dd;
}

.card {
  @include card-surface;
}
~~~

Generated CSS:

~~~css
.card {
  padding: 1rem;
  border: 1px solid #d0d5dd;
}
~~~

If a value must remain configurable in the browser at runtime, a CSS custom property may be appropriate.

## 12. Source maps

A source map links generated CSS back to the Sass files that produced it. Browser developer tools can use it to show original Sass sources while inspecting the compiled page.

Dart Sass generates source maps by default when it writes CSS files.

~~~sh
sass src/styles.scss public/styles.css
~~~

This generally creates the CSS file, a source-map file, and a reference in the CSS that points to the map.

Disable source-map generation when the build does not need it:

~~~sh
sass --no-source-map src/styles.scss public/styles.css
~~~

For production builds, decide whether source maps should be distributed. They can reveal source structure and may embed source contents if configured to do so.

## 13. Source-map URLs and embedded source

By default, Dart Sass uses relative source-map URLs. This lets the map refer to Sass files relative to where the map is stored.

~~~sh
sass --source-map-urls=relative src/styles.scss public/styles.css
~~~

Absolute source URLs are tied to the machine that compiled the CSS and are usually unsuitable for portable output:

~~~sh
sass --source-map-urls=absolute src/styles.scss public/styles.css
~~~

The --embed-sources option places the source contents inside the map. The map may become larger, but the Sass source is available wherever the map is served.

~~~sh
sass --embed-sources src/styles.scss public/styles.css
~~~

Use embedded sources only when that trade-off matches the project. For a public production build, check whether publishing the original Sass content is intended.

## 14. Charset output for non-ASCII text

If generated CSS contains non-ASCII characters, Dart Sass may add an encoding marker: a @charset declaration in expanded output or a byte-order mark in compressed output.

~~~scss
.icon::before {
  content: "→";
}
~~~

Use --no-charset to prevent Sass from adding either marker:

~~~sh
sass --no-charset src/styles.scss public/styles.css
~~~

Choose this option based on the build target and how the CSS files are served.

## 15. A small complete compile example

Save this as src/styles.scss:

~~~scss
// Kept in source only.
$brand: #2457c5;

/*! Copyright and license notice */

$button-radius: 0.5rem;

.button {
  border: 0;
  border-radius: $button-radius;
  color: white;
  background-color: $brand;

  &:hover {
    background-color: #1745a5;
  }
}

/* This comment appears in expanded output and is dropped in compressed output. */
~~~

Compile readable CSS:

~~~sh
sass --style=expanded src/styles.scss public/styles.css
~~~

Compile compact CSS while preserving the license comment:

~~~sh
sass --style=compressed src/styles.scss public/styles.min.css
~~~

Compare both outputs. The rules remain equivalent; whitespace and ordinary comment handling differ.

## 16. Common mistakes

### Expecting // notes to show in CSS

Double-slash comments are silent. Use a block comment when text must appear in expanded CSS.

### Expecting /* ... */ to survive compressed output

Ordinary block comments are stripped in compressed mode. Prefix a required notice with /*!.

### Using a loud comment for a source-only note

A loud comment is part of generated CSS in expanded mode. Use // or /// for notes that should stay in the Sass source.

### Editing the compiled CSS instead of the Sass

A later Sass build will overwrite manual changes to generated CSS. Edit the source SCSS and compile again.

### Publishing source maps without checking their contents

Source maps can identify source paths, and embedded-source options can include the full Sass contents. Make a deliberate build decision.

### Assuming compressed output changes the design

Compression changes formatting and removes optional comments; it should not change the intended CSS behavior.

Before moving on, make sure you can answer these questions:

1. Which SCSS comment type is never emitted as CSS?
2. Which comment form is normally emitted in expanded CSS?
3. Which comment prefix preserves a notice in compressed output?
4. What does --style=expanded control?
5. What does --style=compressed control?
6. What information does a source map provide?
7. How can source-map generation be disabled?
8. What can --embed-sources put in a source map?
9. Where should a fix be made: the SCSS input or generated CSS?
10. How does nesting appear in the compiled stylesheet?
